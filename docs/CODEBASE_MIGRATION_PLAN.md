# Agent Lab codebase migration plan

Status: **proposal for human review**, 2026-10-05. [AGENTS.md](../AGENTS.md) remains the sole project-level instruction and continuity authority. This plan follows the [repository audit](REPOSITORY_AUDIT.md) of baseline `e0465e3161406eb037c324333dff00cfeff7a07b` and the current working-tree instructions. No stage below has been implemented by the audit/cleanup task.

The minimum justified transformation is a small experiment-and-result layer with execution delegated to adapters. Reuse tested integrity, provenance, and validation techniques; do not turn the existing workflow scheduler into the new platform core. Keep the current baseline runnable while an independent offline experiment slice earns its replacement role.

## A. Smallest target responsibilities

The following are responsibilities, not approved schema names or a universal ontology:

| Responsibility | Minimum useful content and boundary |
| --- | --- |
| Experiment definition | A question/hypothesis, controlled factors, treatment/baseline bindings, task-set references, evaluation revision, repeat/seed policy, and resource limits. Freeze a resolved definition before execution. |
| Tasks and datasets | Versioned inputs, source/content identity, expected outputs or evaluation references, split membership, and permitted use/disclosure. Begin with a small local task set; do not build ingestion infrastructure first. |
| Runs and results | Definition/task identity, effective execution binding, submission/repetition identity, observable outcomes, failures, outputs, evaluation records, latency, and usage/cost when available. Distinguish missing measurement from zero; retain unsuccessful runs. |
| Provenance | Code/dependency versions, configuration digest, model/provider/version when exposed, harness/runtime settings, tools/skills, input/source revisions, representation transforms, and artifacts. Record unavailable facts explicitly; never invent hidden reasoning or model state. |
| Artifacts | Exact retained bytes, content hashes, size/media/schema identity, producing run/task, and source/transformation lineage. References may identify text, JSON, files, images, or other media; artifact format is not a universal communication format. |
| Evaluation | Versioned deterministic checks and, only when needed, separately identified evaluators with their own model/configuration and uncertainty. A provider's `pass` report is an observation, not benchmark ground truth. |
| Execution adapters | A bounded invocation that translates resolved inputs, model/harness binding, tools/permissions, and outputs. Declare supported capabilities and retain submission identity and failure evidence. Framework session/checkpoint objects stay behind this boundary. |
| Representation strategies | Replaceable transforms or references with version/configuration, input/output identity, and measured overhead. Separate selection, representation, recipient, retrieval, and scheduling factors. Support a native/simple baseline before proposing an optimizer. |
| Publication boundary | The same inspectable records can feed local analysis and later public results. Record intended visibility and dataset/artifact restrictions; publish only an explicitly selected, sanitized export. No hosted authorization system or commercial plan is needed for the first slice. |

Do not require a worker profile, fixed workflow graph, calibrated router, Git worktree, natural-language message, JSON payload, or hosted runtime for every experiment. A single-agent or model-only task should fit without pretending to be a six-stage code-development workflow. Later multi-agent and embodied experiments may supply adapter-specific structures without redefining all existing records.

| `domain/decisions.py`, deterministic/fake decision engines | Adapt selectively for a later bounded-decision experiment; defer from the first slice | Identity, stale-evidence rejection, abstention, score-semantics checks, and calibration provenance are useful. | `WorkerBackend`, fake workers, manual clock/barriers | Adapt test techniques and a smaller experiment invocation seam | Keep controlled ordering, failure injection, and deterministic timing. The current protocol requires `AgentRunSpec` and legacy lifecycle methods; do not make it the permanent generic experiment API without a compatibility use case. |
| Codex backend, output bridge, process owner, stdio/socket bridge, pinned evidence fixtures | REVIEW: optional comparison adapter or later deletion | Keep only if a concrete experiment needs this harness baseline. There is no existing experiment-domain implementation to keep as-is. That absence justifies a small new layer; it does not justify a replacement general-purpose orchestrator. Decisions, artifacts, and snapshots supply reusable techniques rather than an already generic platform.

## C. Execution stack and boundary

The preferred stack in `AGENTS.md` is consistent with the official sources verified below: Deep Agents as the initial harness, LangChain/LangGraph where it uses or exposes them, and AgentCore Runtime as preferred hosted execution. No material conflict was found.

Treat **harness**, **hosting**, and **model inference** as separate bindings. A local Deep Agents invocation and a hosted invocation should consume the same reviewed experiment intent; a different harness or provider should be selectable without changing stored generic records. AgentCore hosting does not require Bedrock model inference. SDK objects, framework messages/checkpoints, service ARNs, transport/session state, and provider-specific options belong in adapter configuration and bounded provenance references.

Use harness-native tools, subagents, context handling, and checkpoint facilities where useful. Deterministic code still validates resource/permission limits, enables tools, owns state changes, and executes evaluation rules. A framework interrupt is not sufficient evidence that a side effect settled. Durable experiment records and output artifacts must survive beyond an ephemeral hosted compute lifecycle.

Do not select Browser, Code Interpreter, Memory, Gateway, A2A, or a hosted database merely because AgentCore offers them. Use them only when a workload needs them and record their capabilities as experimental factors. Pin the tested stack when implementing an adapter; this audit adds no dependency.

## D. Staged sequence and exit gates

Removing the scheduler first would break the existing suite while delivering no experiment capability. An additive offline slice followed by explicit retirement minimizes that gap. The brief overlap is a migration dependency, not an archive of obsolete active documentation.

| Stage | Bounded change | Exit evidence and review gate |
| --- | --- | --- |
| 1. Review the small experiment contract | Agree a first controllable task family, definition/run/evaluation/artifact identities, factor separation, visibility, and the legacy data/Codex retention choices. Choose package naming and a distinct store boundary. | Human review of generic persisted contracts and any scope-narrowing choice. No adapters, schema migration, or legacy deletion before this gate. |
| 2. Build one offline experiment slice | Add the approved minimal contracts, deterministic definition resolution, one fake execution adapter, versioned deterministic evaluation, result/provenance persistence, and a CLI/API rerun path. Reuse small hashing/artifact primitives only where cheaper than carrying old dependencies. One sequential run is sufficient. Make experiment resources explicit rather than relative to the source checkout. | Known fixture input yields the expected output/evaluation, immutable provenance, verified bytes, and an inspectable failure record. A rerun is attributable; the legacy suite still passes. New modules do not import Codex/framework types or require workflow presets. Installed-package smoke and archive-content checks protect independent reruns and exclude local developer settings. |
| 3. Retire old product machinery | After confirming data requirements, remove the old coordinator/ledger contracts, config loader, specialist/workflow presets, associated schemas/tests, and dead scripts. Extract useful integrity tests first. Isolate an optional Codex adapter only if the comparison use case was accepted. | An explicit reviewed deletion list and data/export decision; no implicit conversion or erasure of user databases. Source/schema/config references have no orphans; offline experiment and package checks pass. Dependency extras and naming update together. |
| 4. Add local Deep Agents execution | Add a thin adapter using the reviewed invocation seam, an explicit replaceable model binding, validated tools, and selected filesystem/checkpoint policy. Capture effective harness/configuration and observable outputs/usage. | Explicitly authorized bounded model invocation; input/output identities, evaluator separation, missing-cost handling, timeout/failure/interrupt behavior, and at least one alternate binding or deterministic contract test. Native defaults are recorded as the baseline. |
| 5. Add AgentCore hosting | Host that same invocation through a selected documented transport/package option. Keep AWS session/deployment/configuration translation outside generic contracts; export durable results/artifacts outside ephemeral compute. | Explicit authorization for resource creation and billable calls. A deployed smoke test verifies packaging, health/invocation, isolation, outputs, durable retrieval, measured latency/usage, and bounded failure cleanup. Do not infer this from local success or documentation. |
| 6. Run the first controlled benchmark | Use a versioned task set, strong native/simple baselines, held-fixed bindings, predeclared evaluation, repetitions/seeds, and one isolated interface factor. Include encoding/decoding/retrieval overhead and failed runs. | Inspectable per-task results, reproducible invocation/configuration, aggregate comparisons with sample sizes/uncertainty, actual cost basis when available, and retained negative results. A gain from selection/scheduling cannot be claimed as a representation gain. |
| 7. Expose selected results | Start with an export/report and a read-only result view using the same records. Add rerun instructions, source/license provenance, and adapters/experiment contribution guidance. | Explicit publication selection, artifact visibility check, independently runnable examples, and an owner-chosen repository license. No frozen UI topology or marketplace prerequisite. |

Each stage should leave its predecessor runnable. Later work should update the active plan as evidence arrives; do not recreate the old milestone/task queue alongside `AGENTS.md`. Prefer an existing abstraction or adapter before extending generic contracts.

## E. Explicit non-goals

- A new general-purpose orchestrator, manager agent, or custom distributed scheduler.
- A universal agent protocol, semantic ontology, workflow graph, or communication representation.
- Completing the old coding-workflow, worktree-integration, intervention, or Codex roadmap before an experiment can run.
- A giant skill/tool/agent marketplace, broad provider catalog, or premature commercial architecture.
- Production adaptive communication optimization before controlled experiments establish its value.
- Mandatory long-term memory, every AgentCore service, hidden-reasoning capture, or assumed cross-provider equivalence.
- A production dashboard, fixed navigation/graph terminology, multi-tenant procurement controls, or paid-feature packaging for the first prototype.
- Automatically migrating, dropping, or rewriting old databases or publishing private inputs/results.

## Official execution-stack verification

Checked against official primary sources on **2026-10-05**. This is documentation verification, not an installed dependency check, executable integration test, deployment, or evidence of benchmark performance.

### Documented support

- **Deep Agents is an available initial harness.** The standalone Python library uses LangChain agent building blocks and the LangGraph runtime. Its documented capabilities include tools, configurable filesystem backends, context management, subagents, and approval interrupts. Planning is opt-in starting in v0.7, so experiments must record enabled capabilities rather than assume that every release has the same defaults. [Deep Agents overview](https://docs.langchain.com/oss/python/deepagents/overview)
- **The lower layers remain accessible.** Deep Agents accepts custom tools, middleware, backends, checkpointers, and stores; its customization examples use LangChain chat-model objects and LangGraph checkpoint/store primitives. These are implementation integration points, not a reason to put their types into generic persisted experiment records. [Deep Agents customization](https://docs.langchain.com/oss/python/deepagents/customization)
- **Model selection can remain replaceable.** Deep Agents supports LangChain chat models with tool calling; callers can supply provider/model identifiers or a configured model instance. Provider integrations and capabilities still need validation for each chosen model. The documented interchange point supports replacing bindings; it does not establish equal behavior or performance across providers. [Deep Agents models](https://docs.langchain.com/oss/python/deepagents/models), [model configuration examples](https://docs.langchain.com/oss/python/deepagents/customization#model)
- **AgentCore Runtime explicitly supports LangGraph and external models.** AWS provides a LangGraph example that wraps `graph.invoke` in a `BedrockAgentCoreApp` entrypoint. AWS describes Runtime as supporting custom/open-source frameworks and models both inside and outside Amazon Bedrock. Hosting on AgentCore therefore does not require choosing Bedrock model inference. [AWS framework integrations](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/using-any-agent-framework.html), [AgentCore FAQ](https://aws.amazon.com/bedrock/agentcore/faqs/)
- **Hosting has a concrete service contract.** AgentCore documents HTTP, MCP, A2A, and AG-UI protocols. For a custom HTTP container, the documented requirements include ARM64, binding to `0.0.0.0:8080`, `POST /invocations`, and `GET /ping`; optional WebSocket communication uses `/ws`. HTTP responses may use JSON or SSE. Other protocols have distinct paths, ports, and envelopes. Keep those details in a hosting adapter. [Runtime service contract](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-service-contract.html), [HTTP contract](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-http-protocol-contract.html)
- **Containers are one deployment option.** AWS also documents direct deployment of code and dependencies as a ZIP archive. Direct deployment still has Runtime requirements; its managed language runtime receives automatic patches, while application dependencies remain the caller's responsibility. Packaging choice must be evaluated rather than treating Docker as universally required. [Direct code deployment](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-get-started-code-deploy.html)
- **A hosted session is not automatically a durable experiment record.** By default, memory and disk state persist only for the compute lifecycle. AWS documents persistent session storage as an option and requires the application to manage user/session mappings. Lifecycle defaults are 15 minutes idle and 8 hours maximum compute lifetime; the documented upper bound is 8 hours for microVMs and 14 days for Instances capacity providers. Invocation limits are separate, including a documented 15-minute synchronous request limit. [Runtime sessions](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-sessions.html), [lifecycle settings](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-lifecycle-settings.html), [Runtime quotas](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/bedrock-agentcore-limits.html)

### Inference and validation boundary

**Inference:** Deep Agents' LangGraph execution interface plus AWS's documented LangGraph entrypoint pattern make a thin Deep Agents hosting adapter a plausible first prototype. The sources checked do not establish that this repository's future combination of package versions, tools, filesystem/sandbox backend, interrupts, checkpointing, and streaming works together on AgentCore Runtime.

AWS has published a Deep Agents example using AgentCore **Browser, Code Interpreter, and Memory**. Those are separate services; that example is not evidence that the same agent was deployed on **Runtime**. [AWS Deep Agents example](https://aws.amazon.com/blogs/machine-learning/build-context-rich-research-agents-with-deep-agents-and-bedrock-agentcore/)

Before accepting an execution adapter, pin and record tested dependency versions; validate the model's tool-calling behavior; run a bounded local invocation with deterministic tool authority and structured results; and then test the chosen hosted package/protocol, session isolation, timeout/failure behavior, persistence, interrupts, and streaming. Capture runtime configuration, package/artifact identity, outputs, evaluations, latency, and measured cost. Documentation support alone establishes neither production compatibility nor reproducibility guarantees. No installation, credential configuration, model call, AWS resource creation, or live deployment was performed for this verification.
